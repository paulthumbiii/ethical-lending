1. PROJECT OVERVIEW

What it is. “Ethical Lending” is a loan management system for a Kenyan digital lender. It runs the whole life of a loan:

signing up borrowers, with data-protection consent
collecting and reviewing M-Pesa statements as evidence
deciding credit limits
disbursing and collecting money through M-Pesa
keeping an append-only double-entry ledger
restructuring struggling borrowers’ loans
collecting debts fairly
producing regulatory reports

It has two web front ends: a desktop dashboard for lender staff and a mobile-first portal for borrowers. Theme: “lending that shows its working”, meaning every charge is explained and the borrower can see their legal protections.

Hard constraints / non-negotiable rules. These come from the user’s own project dossier. I have not independently verified the legal citations ⚠️; treat them as the user’s specification.

In-duplum (Banking Act Cap 488, s.44A): after a loan defaults (90 days overdue), interest + penalties + collection fees can never exceed the principal outstanding at default. When reached, is_in_duplum_locked = true and all further charges freeze.
Fair debt collection (CBK Digital Credit Providers Regulations 2022, Reg. 20): no contact-book scraping, no shaming, no contacting friends or relatives; outreach only 08:00-18:00 East Africa Time; 48-hour cooldown per borrower between automated contacts; an active Promise-to-Pay pauses escalation.
Data protection (Kenya Data Protection Act 2019): informed consent recorded with IP, user agent and timestamp before processing a loan. Consent for reading M-Pesa statements is a required tick box on the upload form, written to the audit trail. Personal data should not be kept longer than needed ⚠️ (no retention job exists yet for statement files).
Excise duty: 20% on processing/admin fees; the GL splits fee postings 80% revenue / 20% KRA excise payable. ⚠️ See the excise note in section 8: the code treats the 20% as part of the fee, not on top of it. Verify the legal rule with the user before any real use.
CRB Regulations 2020: 30-day pre-listing notice before sharing adverse data; dispute locks stop reporting.
Money rules: all money columns DECIMAL(12,2); no floats in calculations; use BCMath (bcadd, bcsub, bcmul, bcdiv, bccomp) on strings. number_format((float) $x, 2) is allowed for display only.
Code rules: declare(strict_types=1), backed enums, FormRequests, service classes, transactions and lockForUpdate() where money or state moves.
Platform rule: the user works in Windows cmd.exe (8,191-character command limit): no giant inline commands or multi-line shell scripts.

Honest framing already given to the user: “industrial” is not measured in tables or pages. The hard core (ledger, GL, in-duplum, maker-checker, audit, idempotency, tests) is strong. What is missing is the operations UI (Phase 11, then a Phase 12), proof against real Safaricom, production running (queue worker, scheduler, backups, monitoring), and staff security (2FA, password reset, session timeout).

Completed phases: what was built and why (summary of choices)
Append-only ledger. Balances always come from the latest loan_ledger_entries row; never updated in place.
Payment waterfall order: fees and penalties, then interest, then principal; leftover becomes overpayment credit; runs under lockForUpdate().
Restructuring: eligibility needs repayment ratio ≥ 0.30 (no loans counts as 1.00; loans with no repayments counts as 0 and is refused); forgives 100% of fees, keeps interest, splits the rest into two instalments, expires in 7 days.
Auth: hand-written login (email or phone plus password), no Breeze, single web guard; inactive and role-less accounts are blocked. Auth audit rows are written by a listener (RecordAuthActivity) on Laravel’s Login, Failed and Logout events. It masks identifiers and never stores passwords.
Role gates in one place: UserRole helpers feed both routes and nav.
Collections workbench is read-only by construction.
Security choices: payment phone numbers come only from the DB; loans are looked up through $borrower->loans() so another borrower’s id returns 404; throttles on login, register, apply, statement upload and payments; FormRequests always authorize() true because role middleware on the route does access control.
Apply page (11.1): one open application or active loan at a time, enforced with lockForUpdate() on the borrower row inside a transaction; whole-shilling amounts validated against product min/max with BCMath; tenure = product default; credit limit deliberately not checked at application time (the engine derives the limit from the request).

Why 11.2 to 11.2c exist. The underwriting engine’s Rule 4 (M-Pesa inflow ≥ 1.5 × requested principal) originally trusted a number a staff member typed. Self-registered borrowers have inflow 0 and would all be rejected. The user wanted real evidence: borrowers upload detailed M-Pesa statements, staff review them, the applicant sees the state, and forgery is considered (“people tend to forge these documents”). So the inflow figure is now set only by accepting an uploaded statement.

11.2 (staff queue). lender.applications.* routes. lender_admin and credit_officer can open the queue and act (UserRole::underwriters()); finance_officer can view only (UserRole::applicationViewers() includes finance). Pages: lender/applications/index.blade.php (waiting list, recently checked) and show.blade.php.

11.2b (borrower upload). Statement card on the Apply page. PDF only (extension plus %PDF- header check), max 5 MB, stored privately under storage/app/private/statements/{borrower_id}/{random 40 chars}.pdf (disk local, root storage/app/private). SHA-256 recorded. The optional PDF password is stored encrypted with Crypt (APP_KEY) and erased when staff decide. Consent tick box required and audited. A newer upload supersedes one still waiting. Automated flags (staff-only, never shown to the borrower): same_file_other_borrower, same_file_earlier_application. Uploads only allowed while the application status is submitted or pending, and not after a statement was accepted. Ownership: another borrower’s application returns 404.

11.2c (staff review). On the application page an underwriter sees each statement with name, size, fingerprint (first 12 hex chars) and flags. They can:

Open the PDF (streams from the private disk, audited as STATEMENT_VIEWED).
Show the password (flash message shown once, audited as STATEMENT_PASSWORD_REVEALED, password never written to the audit row).
Accept (staff type the verified average monthly inflow; flagged statements require a written note; sets valid_until = today + 30 days; erases the stored password; updates borrower_financial_profiles.mpesa_average_monthly_inflow with old and new values audited as STATEMENT_ACCEPTED).
Reject (written reason required, shown to the borrower; erases the password; audited as STATEMENT_REJECTED).
Gate: ApplicationReviewService::runCheck() throws RuntimeException('Accept a valid M-Pesa statement before running the credit check.') unless an upload for that application has review_status = accepted and valid_until >= today (whereDate).

Decision (user chose option 2): the fee is added to the balance. The borrower receives the full principal and owes principal + fee. The M-Pesa amount stays equal to the principal.

app/Services/Lending/LoanFeeService.php:
quote(Loan) computes fees from FeeMatrix rows. percentage = percent of principal rounded half up to the cent (BCMath: bcadd(bcdiv(bcmul(principal, pct, 4), '100', 4), '0.005', 2)); fixed or flat = fee_amount; any other type is skipped.
charge(Loan, receipt) writes one FEE_CHARGED ledger entry per fee through LoanLedgerService::recordEntry, then a GL posting (recordFeeWithExcisePosting for excise-applicable fees, otherwise a plain 1200/4020 entry), and an audit row LOAN_FEE_CHARGED. It does nothing if a FEE_CHARGED ledger row already exists for the loan.
chargedTotal(Loan) sums the debits of the loan’s FEE_CHARGED rows.
assertLedgerReady(Loan) throws RuntimeException('The ledger is missing accounts (…). Run the ChartOfAccountSeeder before sending money.') if 1010 or 1200 is missing, or 4020 (and 2030 when any quoted fee carries excise) when the product has a fee.
B2cDisbursementService (replaced again): processCallback now calls a private chargeFees() after the GL posting. It runs inside DB::transaction (a savepoint) wrapped in try/catch; on failure it rolls back only the fee, logs to the daily channel and writes audit LOAN_FEE_CHARGE_FAILED, so the loan is still recorded as disbursed. Reason: money has already left; losing the disbursement record is worse than a missing fee.

⚠️ Coursework, portfolio or real product: unanswered.
⚠️ Sample statement format: unanswered (blocks 11.2e).
⚠️ Excise on fees. The code treats the fee as the amount the borrower owes (5% of principal) and splits 20% of it to excise payable. Kenyan excise on lender fees is normally charged on top of the fee. I flagged this to the user; he did not respond. Verify before anything goes live. If it should be on top, it is a small change in LoanFeeService/GeneralLedgerService::recordFeeWithExcisePosting.
⚠️ fintech log channel. CreditUnderwritingEngine, MakerCheckerService, the parser and LoanLedgerService::recordEntry call Log::channel('fintech'). Once, a failing run showed InvalidArgumentException: Log [fintech] is not defined from CreditUnderwritingEngine.php:151; an earlier agent called that a “harmless red herring” without verifying. LoanLedgerServiceTest calls it and passes, so it is probably defined, but I never saw config/logging.php. New relevance: if undefined, 11.4c’s fee would fail inside its savepoint and only show as audit LOAN_FEE_CHARGE_FAILED. If ever seen, ask the user to run type config\logging.php > files_for_logging.txt and check for fintech.
⚠️ MpesaStatementParserService cannot be trusted for real statements. It is NOT called by the upload flow. It takes the first amount on each line (may be the balance), classifies inflow by keywords, divides by a hard-coded 3 months, ignores the PDF password, smalot/pdfparser is not installed (it falls back to raw bytes), and it writes inflow straight into the profile without review or audit. The mock fallback (fake KES 50,000/month when the file is missing) runs only when app()->environment('testing'). Rewrite or replace it in 11.2e; make it only propose a figure, never write to the profile.
⚠️ No retention or deletion policy for statement PDFs. No malware scan. The “PDF” check is a header check only.
⚠️ Statement reuse across applications is not built (valid_until is 30 days but the gate only looks at statements of the same application).
⚠️ Tiered rigor is only an idea (section 8); do not build without asking.
⚠️ B2cDisbursementService::initiateDisbursement makes the Safaricom HTTP call inside a DB transaction holding a row lock. If the HTTP call throws (no keys locally, or a network failure), the transaction rolls back and no disbursement row is saved, but the loan row created earlier by LoanOriginationService (a separate committed transaction) remains. If Safaricom accepts the request but our process dies before the row is saved, the money could go out with no record; there is no reconciliation job. Consider moving the HTTP call outside the transaction with a persisted initiated row first.
⚠️ No staff way to resolve a B2C timeout (disbursement stuck in initiated). A stuck row blocks a second payout by design.
⚠️ B2C callback endpoints are unauthenticated; add Safaricom IP allow-listing before production. ⚠️ config/mpesa.php lacks initiator_name and security_credential (defaults testapi/testcredential are used).
⚠️ DispatchMpesaB2cDisbursementJob calls initiateDisbursement directly. The job has tries = 3 with backoff. The new guard means a retry after a partial success is refused, which is safe, but the job is not used by the new UI flow (the controller calls the service synchronously). Decide whether to keep or remove it.
⚠️ Race: in a true simultaneous duplicate C2B callback, the unique index on trans_id rejects the second insert; a catch converts it to DuplicateWebhookException. Cannot be reproduced in a single-process test.
⚠️ In-duplum cap source: borrower meter and collections workbench read in_duplum_tracking.statutory_cap_limit; lender dashboard reads default_principal_snapshot. Assumed equal.
⚠️ Workbench cap label: in_duplum_tracking stores only post-default interest and penalties; the statutory cap also counts collection fees, so the workbench column is labelled “Charged since default”.
⚠️ “You owe in total” on the borrower screen = principal + interest + fees from the latest ledger row. With 11.4c the fee now appears there automatically. Adjust BorrowerPortalService::summary() if the lender’s definition differs.
⚠️ config/mpesa.php has the stk_callback_url key now (seen in the dump). .env still needs MPESA_STK_CALLBACK_URL= (not confirmed). STK Push cannot send real prompts until a public HTTPS callback URL exists (for example ngrok). Pressing Pay locally shows “payment prompts are not switched on”, which is expected.
⚠️ --text-2xs: 0.6875rem; and --text-3xs: 0.625rem; in the @theme block of resources/css/app.css: not confirmed.
⚠️ Registration edge not closed: BorrowerOnboardingService checks the phone against users, and the request checks ID and email against borrowers, but nothing checks whether a borrowers row with that phone already exists without a login (created by USSD or staff). ⚠️ Unknown whether borrowers.phone_number has a unique index. A fix was offered; the user did not answer.
⚠️ Maker-checker execution gap: approving any action type other than APPROVE_LOAN_APPLICATION records approval and an audit row but executes nothing (for example WAIVE_INTEREST does not touch the ledger). Making it fail closed would break MakerCheckerDeskTest (approves WAIVE_INTEREST) and LenderDashboardTest (uses loan_disbursement). The proper fix is a per-action-type executor. Ask the user before touching it.
⚠️ The ledger has two entry-type vocabularies: older code writes lowercase disbursement and repayment (the waterfall and B2C service), while LoanLedgerService uses uppercase types (DISBURSEMENT_PRINCIPAL, FEE_CHARGED, REPAYMENT_*). The 11.4c fee uses FEE_CHARGED through LoanLedgerService, which reads the latest row’s running balances correctly regardless of the previous row’s type. Do not “fix” the mix without checking every consumer.
⚠️ LoanLockingMysqlTest takes about 144 s per test on MySQL (unmeasured since the cleanup fix). Normal SQLite suite: 46.58 s on the last run (it has varied from 61 s to 289 s on this laptop). Looks like laptop or antivirus slowness. Not investigated.
⚠️ Password reveal uses a session flash, so the password appears in the page HTML once for the staff member who requested it. Acceptable for now.

Architecture decisions and reasons (11.2 to 11.4c)
Statements only propose; humans decide. Software cannot prove a PDF is genuine. Automated checks produce flags; a credit officer decides, writes a note when flags exist, and is named in the audit trail. Never auto-blacklist someone on a forgery flag (Data Protection Act, CBK digital-credit fairness).
Flags are staff-only so the borrower is not tipped off and no other borrower’s data leaks.
Documents are visible only to people who decide on them (lender_admin, credit_officer). Finance can see the page but not the PDF or the password.
The PDF password is stored encrypted and erased on decision.
Rule 4’s figure comes from the accepted statement (staff type the verified average monthly inflow); statements are tied to one application and valid 30 days.
Rejecting a statement keeps the application pending; rejecting at the credit-check stage rejects the application.
Two-person approval (11.3): the maker can never decide their own request; approval refuses unless the application is still approved_pending_checker.
Money-out separation of duties (11.4b): the credit officer who builds a case cannot send the money; only finance officers and lender admins can. ⚠️ A lender admin can both approve (as second approver, if not the maker) and send money; no rule prevents the same admin doing both steps. Raise with the user if tighter control is wanted.
Whole-shilling principal, rounded down (11.4a): M-Pesa B2C sends whole shillings and the ledger must equal what was actually sent.
Never lose a disbursement over a fee (11.4c): the fee runs in a savepoint and is allowed to fail; the loan is still recorded as disbursed.
Check the ledger before sending money (11.4c): missing GL accounts block the payout up front.
